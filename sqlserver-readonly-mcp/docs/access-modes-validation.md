## 85 秒等待的定位与修复

此前把该次等待描述成“已提交行情查询，数据库超时未返回”不准确，现更正：程序错误地将本机空白 access.mode 判为非法，在启动配置校验时以退出码 2 退出。空白应按认证使用默认模式，这是产品校验缺陷。阻塞的是临时 Python 探针对 initialize 的等待，SQL 请求尚未发送；因此该案例不能说明数据库连接或执行超时失效。

根因是临时探针忽略 stderr，同时 stdout 读完未通知等待队列。即使子进程已退出，调用线程仍等待 q.get(timeout=85)。85 秒是探针客户端保护值，不是 MCP 配置。

修复为可复用 tests/dev_mcp_probe.py：

- stdout EOF、非法协议输出、断管立即中止等待并报告阶段/退出码。
- 捕获 stderr 供本机诊断，不自动回显可能包含内部信息的内容。
- 请求使用单一绝对截止时间，不因通知消息重新计时；初始化单独限制 5 秒。
- 探针失败后关闭本次独立子进程，不重试、不切换 MCP。

修正产品空值规则前，新探针在 initialize 阶段 81 ms 内报告 process_exited、exitCode=2，证明退出检测已生效。用户测试配置始终未修改。

新增两个 Python 回归：启动退出能及时发现、持续通知不能无限延长请求等待，均通过。新增两个开发版 MCP 协议测试：本机模拟端点接受 TCP 后不回应 SQL 登录握手，必须确认实际接受了连接，防止把未连接成功的其他错误误算作测试通过。

| 访问模式 | connectTimeoutSeconds | 实测工具返回耗时 | 结果 |
|---|---:|---:|---|
| catalog | 5 | 5197 ms | access_check_unavailable；未进入业务执行 |
| development | 5 | 5267 ms | 连接失败；0 行 |

两项均返回中性网络提示。没有修改产品的 5 秒连接／15 秒执行前／60 秒业务阶段设置，也没有新增重试、后台任务或熔断配置。这两个模拟案例验证登录握手无响应，不替代 DNS、物理丢包、执行中断线等全部网络场景的验收。
